## 2. 关键 diff

站点接口：

```diff
- const trains = await Train.find().select('departureCity arrivalCity departureStation arrivalStation').lean();
- res.json({stations: [...new Set(trains.flatMap(...))].filter(Boolean)});
+ res.json({stations: await getStations()});
```

缓存模块 TTL 为 `5 * 60 * 1000` 毫秒；有效缓存返回副本，未命中才读取数据库。空数组可正常缓存；数据库失败不缓存且向原有错误处理中间件传播。管理员写入的事务成功提交后调用 `invalidateStationCache()`，失败事务不会走到失效调用。失效时递增 generation，使失效前的在途查询不能覆盖新缓存。

管理员三个入口各增加：

```diff
  await mongoose.connection.transaction(/* 原有事务 */);
+ invalidateStationCache();
  // 原有响应
```

订单索引：

```diff
  orderSchema.index({userId: 1, status: 1});
+ orderSchema.index({status: 1, expiresAt: 1});
  orderSchema.index({userId: 1, requestId: 1}, /* 原有唯一约束 */);
```

过期清理：

```javascript
let expirationFlight = null;
function expireOrders() {
  if (!expirationFlight) {
    expirationFlight = runExpiration().finally(() => { expirationFlight = null; });
  }
  return expirationFlight;
}
```

原有扫描及逐订单事务移入同文件的 `runExpiration()`，内部仍以 pending＋expiresAt 判断是否取消，并在同一事务内释放库存。未增加 limit，避免改变一次清理覆盖范围；大规模积压的分批策略留待另行评估。

## 3. 写入入口检查

- 在线车次新增、修改、删除都经过管理员控制器，三个入口均已失效缓存。
- 下单的 Train.findOneAndUpdate 只更新 revision，不改变城市/车站，无需因每次下单失效公共站点缓存。
- seed 在独立 CLI 进程导入车次，不是在线 HTTP 写入口；CLI 内调用失效函数不能清除另一个在线进程的内存，因此未加入无效的跨进程失效调用。在线进程在这类外部写入后最多等待五分钟 TTL 刷新。
- 另外检索到 experiments/perf/seed-large.js 的独立批量写入入口，同样属于进程外写入。本轮未修改或运行该脚本，也未改变其数据量或参数。
- 直接数据库写入同理，不能保证立即更新所有实例。

新增测试验证：

1. 首次查询/后续命中、站点去重、响应副本不污染缓存。
2. TTL 为五分钟，截止前命中、恰好到期重新读取。
3. 显式失效立即重新读取。
4. 冷缓存并发请求只查询一次。
5. 失效前旧查询在新查询之后完成，也不会覆盖新缓存。
6. 数据库异常传播，失败不缓存，下一次可恢复。
7. 空站点数组可缓存。
8. expireOrders 并发调用共享一次扫描/事务，结束后新一轮可执行。
9. 清理失败向等待者传播，后续调用可重试。
10. 管理员真实 API 新增、修改、删除后，站点立即刷新，响应结构不变。
11. 临时数据库中的并发清理仅释放一次库存，后续轮次仍正常。
12. 临时数据库实际创建新订单索引，原用户订单索引和唯一约束保留。

## 5. 索引创建方式

索引实际名称为默认的 `status_1_expiresAt_1`，字段顺序 status 在前、expiresAt 在后。它是查询索引，不是 TTL 删除索引，不会绕过订单事务直接删除订单。

现有启动链路 `initializeModels() → Order.init()` 会按 Schema 创建缺失索引，测试中通过真实 collection.indexes() 断言其存在，并同时检查 userId＋status、orderNumber 唯一索引及 userId＋requestId 唯一索引仍存在。

无需新增迁移脚本，不调用 syncIndexes，也没有为本次优化删除任何订单索引。若未来显式禁用 autoIndex，应在获准的维护流程中连接指定数据库后调用 Order.createIndexes() 创建缺失索引。

本轮未重启或重建现有 demo，也未连接 demo 数据库创建索引；不声称运行中的 3000 服务已经加载了新代码或 27018 数据库已经拥有该索引。

## 6. API、权限和事务影响

- 不改前端、API 路径、响应字段或状态码约定。
- 站点接口仍返回 `{stations:[...]}`，仅缓存公共站点，不缓存会话、角色或订单。
- 保留会话校验、角色中间件和用户订单隔离。
- 保留待支付订单过期条件、取消状态及库存释放规则。
- 保留每张过期订单的事务边界与库存更新使用的 session。
- 保留定时器入口已有保护；新的 single-flight 使定时器和 GET /orders 等调用者也能共享同一轮任务。

## 7. 限制与风险

- 缓存与 single-flight 都只在单个 Node.js 进程内有效，多实例各自维护一份；没有新增共享缓存或分布式锁。
- 不同实例、seed 或直接数据库写入不能即时失效其他进程缓存，最多在 TTL 后刷新；多实例需要可靠广播或共享缓存后才能提供跨实例一致性。
- 已经开始的站点读取可能向该请求返回写入前的结果，但不会在失效后重新污染后续缓存。
- 多实例仍可能同时清理；现有数据库条件更新和事务继续承担不重复释放的最终保护，进程内 single-flight 不能当作分布式锁。
- 仍未分批处理大量积压的过期订单；补充测量只覆盖 20 条过期订单的并发清理，不承诺更大积压量下的时延。
- 性能补充测量来自单进程、单节点 Docker 环境；多实例共享缓存、跨进程失效和分布式 single-flight 未测量。
